# 檢測基準明細（二）：4.1.3 交易、4.1.4 鑑別連線、4.1.5 程式碼安全 & 4.2.2 伺服器 Webview

依據：《行動應用 App 基本資安檢測基準 V4.0》（中華民國 113 年 9 月）

## 4.1.3. 交易資源控管安全

### 4.1.3.1. 交易資源使用

#### `4.1.3.1.1` 行動應用程式交易資源使用聲明
- **檢測分類**：`L3`
- **檢測依據**：規範 4.1.3.1
- **技術要求**：行動應用程式應於使用交易資源時主動通知使用者
- **檢測基準**：
  - (1) **線上交易**：檢查於交易**前**是否主動通知使用者，且資訊至少包含**交易商品名稱、金額及交易方式**。（僅限外匯、期貨與虛擬貨幣，可在事前宣告風險並取得同意下，不針對每筆交易額外通知）。
  - (2) **現場交易**：使用者在現場購買商品或服務，交易資訊未顯示在 App 頁面上，但使用者在現場確認並授權交易（特別是行動支付情境），則視為符合，否則不符合。
- **檢測結果**：
  - `符合要求`：符合所有檢測基準，或僅使用其中一項交易模式且符合該項基準。
  - `不符合要求`：不符合檢測基準。
  - `不適用`：行動應用程式僅涉及收款行為。

#### `4.1.3.1.2` 行動應用程式拒絕交易資源使用機制
- **檢測分類**：`L3`
- **檢測依據**：規範 4.1.3.1
- **技術要求**：行動應用程式應提供使用者拒絕使用交易資源之權利
- **檢測基準**：
  - (1) 檢查於交易時是否提供使用者拒絕（取消／中止）交易之功能。（僅限外匯、期貨與虛擬貨幣可在事前宣告風險並取得同意下免每筆提供）。
  - (2) 檢查在使用者拒絕交易的情況下，App 是否未進行交易（未送出扣款或授權請求）。
- **檢測結果**：
  - `符合要求`：符合所有檢測基準。
  - `不符合要求`：不符合任一檢測基準。
  - `不適用`：行動應用程式僅涉及收款行為。

#### `4.1.3.1.3` 行動應用程式交易收款聲明
- **檢測分類**：`L3`
- **檢測依據**：規範 4.1.3.1
- **技術要求**：行動應用程式應於交易收款時主動通知使用者
- **檢測基準**：檢查於交易收款時，是否主動通知使用者，且資訊至少包含**交易對象、交易時間、交易金額及交易商品資訊**。
- **檢測結果**：
  - `符合要求`：符合檢測基準。
  - `不符合要求`：不符合檢測基準。
  - `不適用`：行動應用程式無收款行為。

### 4.1.3.2. 交易資源控管

#### `4.1.3.2.1` 行動應用程式交易資源使用者身分鑑別
- **檢測分類**：`L3`
- **檢測依據**：規範 4.1.3.2、MASVS-AUTH-3
- **技術要求**：行動應用程式應於使用交易資源時進行使用者身分鑑別
- **檢測基準**：檢查於交易前，是否提供有效的身分鑑別機制。
- **檢測結果**：
  - `符合要求`：符合檢測基準。
  - `不符合要求`：不符合檢測基準。
  - `不適用`：行動應用程式僅有預授權交易行為。
- **備註與審核線索**：(1) 除首次交易須身分鑑別外，若屬同一連線（session），第二次之後交易不須再進行身分鑑別；若 session 改變，須重新鑑別。(2) 機制包括但不限於 OTP、生物特徵身分鑑別及 Google Authenticator（須確保生物驗證與密碼／金鑰解除綁定安全，而非僅前端 boolean 回呼）。

#### `4.1.3.2.2` 行動應用程式交易記錄
- **檢測分類**：`L3`
- **檢測依據**：規範 4.1.3.2
- **技術要求**：行動應用程式應提供使用交易資源之交易記錄
- **檢測基準**：檢查於交易後，是否提供查詢交易記錄之管道，且交易記錄至少包含**交易商品名稱、交易時間及交易金額**之記錄。
- **檢測結果**：
  - `符合要求`：符合檢測基準。
  - `不符合要求`：不符合檢測基準。
  - `不適用`：行動應用程式僅有預授權交易行為。

#### `4.1.3.2.3` 行動應用程式授權交易
- **檢測分類**：`L3`
- **檢測依據**：規範 4.1.3.2
- **技術要求**：行動應用程式應提供預授權交易之記錄
- **檢測基準**：
  - (1) 預授權交易功能是否提供查詢交易記錄之管道，包括**交易之金額**。
  - (2) 預授權交易功能是否提供使用者**取消預授權**之功能。
  - (3) 預授權交易功能是否於取得使用者提供之授權時進行**宣告**。
- **檢測結果**：
  - `符合要求`：符合所有檢測基準。
  - `不符合要求`：不符合任一檢測基準。
  - `不適用`：行動應用程式無預授權交易行為（如定期扣款、免密快速扣款、訂閱自動續約）。

## 4.1.4. 行動應用程式使用者身分鑑別、授權與連線管理安全

### 4.1.4.1. 使用者身分鑑別與授權

#### `4.1.4.1.1` 行動應用程式使用者身分鑑別機制
- **檢測分類**：`L2`、`L3`
- **檢測依據**：規範 4.1.4.1、MASVS-AUTH-1
- **技術要求**：行動應用程式應有適當之身分鑑別機制，確認使用者身分
- **檢測基準**：如行動應用程式存取與個人資料相關之敏感性資料，檢查是否提供鑑別機制。
- **檢測結果**：
  - `符合要求`：符合檢測基準，或未存取使用者個人資料相關之敏感性資料。
  - `不符合要求`：不符合檢測基準。
  - `不適用`：經主管機關同意免身分鑑別與授權的情況。
- **審核線索**：檢查存取個資 API 端點或本地個資頁面之前是否有確實驗證流程，避免未經認證即可直接呼叫個資查詢介面或硬編碼繞過登入。

#### `4.1.4.1.2` 行動應用程式使用者身分授權
- **檢測分類**：`L2`、`L3`
- **檢測依據**：規範 4.1.4.1、MASVS-AUTH-1
- **技術要求**：行動應用程式應依使用者身分授權
- **檢測基準**：如行動應用程式存取與個人資料相關之敏感性資料，檢查是否提供身分授權機制。
- **檢測結果**：
  - `符合要求`：符合檢測基準，或未存取使用者個人資料相關之敏感性資料。
  - `不符合要求`：不符合檢測基準。
  - `不適用`：經主管機關同意免身分鑑別與授權的情況。
- **審核線索**：檢查角色／權限控管（RBAC/IDOR 防護）、後端 Token/Claim 驗證與本地功能權限隔離，確保不同身分僅能存取授權範圍內之資源。

### 4.1.4.2. 連線管理機制

#### `4.1.4.2.1` 行動應用程式交談識別碼規則性
- **檢測分類**：`L2`、`L3`
- **檢測依據**：規範 4.1.4.2、MASVS-AUTH-1
- **技術要求**：行動應用程式應避免使用具有規則性之交談識別碼
- **檢測基準**：
  - (1) 是否採用長度為 **128 位元（含）以上**之交談識別碼。
  - (2) 交談識別碼是否**未與時間、使用者提交資料、具規則性之數字或字串有直接關聯**或難以偽造。
  - (3) 交談識別碼是否具備**登出失效機制**。
- **檢測結果**：
  - `符合要求`：符合所有檢測基準，或未使用交談識別碼。
  - `不符合要求`：不符合任一檢測基準。
- **備註與審核線索**：
  - 交談識別碼指使用者身分鑑別後所使用；**JWT 亦納入本項檢測範疇**。
  - 靜態審核重點：檢查登出流程是否僅刪除本地儲存（Client-side delete）卻未呼叫後端撤銷／失效 API（`logout` / `revoke` endpoint），此處常見「只清本地 Token 未通知伺服器失效」之缺口，需搭配後端碼或標註「待人工／動態確認後端 Session/JWT 登出後是否仍可重放」。

#### `4.1.4.2.2` 行動應用程式伺服器憑證有效性
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.4.2、MASVS-NETWORK-1、MASVS-NETWORK-2
- **技術要求**：行動應用程式應確認伺服器憑證之有效性
- **檢測基準**：
  - (1) 伺服器憑證是否仍於有效期間內、未被註銷（Revoke），且憑證主體名稱（CN）與主體別名（SAN）包含連線之伺服器網域名稱。
  - (2) 是否使用**憑證綁定（Certificate Pinning）**方式驗證，確保連線之伺服器為 App 開發者所指定；若無法預期使用者所連線之網站，則應提示連線目標有變更並有提醒使用者即將連線至其他網站之設計。
- **檢測結果**：
  - `符合要求`：符合所有檢測基準。
  - `不符合要求`：不符合任一檢測基準。
- **審核線索**：
  - 嚴查「自訂 `TrustManager` / `X509TrustManager` 空實作」、「`HostnameVerifier` 回傳 `true`」、「`URLSessionDelegate` 無條件接受 `URLAuthenticationChallenge`」或 `WebViewClient.onReceivedSslError` 呼叫 `handler.proceed()`（**一律判定不符合要求**）。
  - 檢查是否配置憑證綁定：Android `network_security_config.xml` `<pin-set>` 或 OkHttp `CertificatePinner`；iOS `URLSession` 公鑰/憑證比對（`TrustKit` / `SecTrustEvaluateWithError` + hash pin）；Flutter `SecurityContext` / `HttpClient.badCertificateCallback`（不可直接回傳 `true`）。

#### `4.1.4.2.3` 行動應用程式伺服器憑證簽發來源
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.4.2、MASVS-NETWORK-1
- **技術要求**：行動應用程式應確認伺服器憑證為可信任之憑證機構所簽發
- **檢測基準**：檢查是否驗證並確保伺服器憑證為行動作業系統內建可信任之憑證機構（CA）所簽發。
- **檢測結果**：
  - `符合要求`：符合檢測基準。
  - `不符合要求`：不符合檢測基準。
- **備註與審核線索**：若 App 僅運用於封閉式內網連線，企業自行簽發的憑證亦可視為可信任憑證。檢查是否誤將未受信任之測試自簽憑證或全域 `trustAll` 邏輯留存於正式版本（Release build）。

#### `4.1.4.2.4` 行動應用程式封包流向
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.4.2、MASVS-NETWORK-2
- **技術要求**：行動應用程式封包流向應與所宣告的內容一致
- **檢測基準**：檢查封包流向是否與「附錄三基本資安檢測資料調查表」宣告的封包流向（國家與網域名稱）一致。
- **檢測結果**：
  - `符合要求`：符合檢測基準。
  - `不符合要求`：不符合檢測基準。
- **審核線索**：盤點程式碼及第三方 SDK（如廣告、推播、分析、地圖、Crash 回報 SDK）所有外連網域，與使用者提供之調查表欄位 20、21 比對；若缺調查表或無法確認第三方 SDK 執行期網域，標記為「待人工／動態確認」並列出程式碼中發現的所有網域清單。

## 4.1.5. 行動應用程式碼安全

### 4.1.5.1. 防範惡意程式碼與避免資訊安全漏洞

#### `4.1.5.1.1` 行動應用程式惡意程式碼
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.5.1
- **技術要求**：行動應用程式應避免含有惡意程式碼
- **檢測基準**：
  - (1) 是否未針對其他 App 或作業系統之檔案，在未授權情況下嘗試查詢、新增、修改、刪除、存取遠端服務、提權（如 `su` 提權、未授權存取其他App沙盒）。
  - (2) 是否未包括可導致作業系統發生未預期錯誤、資源明顯耗損、重新啟動或關閉等行為。
- **檢測結果**：
  - `符合要求`：符合所有檢測基準。
  - `不符合要求`：不符合任一檢測基準。
- **備註**：常見惡意程式類型含網路釣魚（Phishing）、殭屍網路（Botnet）、間諜軟體（Spyware）及下載器（Downloader，動態下載未經驗證的 DEX/SO/程式碼執行）。檢查是否有 `DexClassLoader` 動態載入外部未驗證執行檔、隱藏背景竊聽／簡訊／通訊錄上傳行為等。

#### `4.1.5.1.2` 行動應用程式資訊安全漏洞
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.5.1、MASVS-CODE-3、MASVS-CODE-4
- **技術要求**：行動應用程式應避免資訊安全漏洞
- **檢測基準**：檢查行動應用程式是否不存在已知安全性漏洞。
- **檢測結果**：
  - `符合要求`：符合檢測基準。
  - `不符合要求`：不符合檢測基準。
- **備註**：**不符合本項檢測基準之已知安全性漏洞，為具 CVE 編號且 CVSS v3.0 分數大於等於 7（嚴重等級為 High 或 Critical 者）之漏洞。**（亦須注意常見高風險程式碼安全弱點如路徑遍歷、反序列化漏洞、WebView `setAllowFileAccess(true)` / `addJavascriptInterface` 濫用等）。

#### `4.1.5.1.3` 行動應用程式針對螢幕覆蓋攻擊進行防護
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.5.1、MASVS-PLATFORM-3
- **技術要求**：行動應用程式應針對螢幕覆蓋攻擊進行防護
- **檢測基準**：檢查是否針對螢幕覆蓋攻擊（Screen Overlay Attack / Tapjacking）進行防護或主動警示使用者。
- **檢測結果**：
  - `符合要求`：符合檢測基準。
  - `不符合要求`：不符合檢測基準。
  - `不適用`：**iOS 作業系統之應用程式**。
- **審核線索（Android）**：檢查關鍵畫面／交易／登入／權限請求 View 是否設定 `android:filterTouchesWhenObscured="true"`、`setFilterTouchesWhenObscured(true)`，或針對 Android 12+ 設定 `window.setHideOverlayWindows(true)`（需 `HIDE_OVERLAY_WINDOWS` 權限）或覆寫 `onFilterTouchEventForSecurity()` 檢查 `FLAG_WINDOW_IS_OBSCURED` / `FLAG_WINDOW_IS_PARTIALLY_OBSCURED`。

### 4.1.5.3. 函式庫引用安全

#### `4.1.5.3.1` 行動應用程式函式庫引用安全
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.5.3、MASVS-CODE-3
- **技術要求**：行動應用程式於引用之函式庫有更新時，應備妥對應之更新版本
- **檢測基準**：檢查 App 引用之函式庫是否不存在已知安全性漏洞（**具 CVE 編號且 CVSS v3.0 ≥ 7，High / Critical**）。
- **檢測結果**：
  - `符合要求`：符合檢測基準。
  - `不符合要求`：不符合檢測基準。
- **備註與審核線索**：須於附錄三調查表自我宣告引用函式庫名稱及版本資訊。檢查 `build.gradle*` / `libs.versions.toml` / `Podfile.lock` / `Package.resolved` / `pubspec.lock` / `package-lock.json` 與原生 `.so`/`.xcframework` 依賴；若環境有 lockfile 稽核工具或已知高危版本則實檢，無法即時查詢 CVE 資料庫者標註已知清單並提醒執行 SCA 掃描。

### 4.1.5.4. 使用者輸入驗證

#### `4.1.5.4.1` 行動應用程式使用者輸入檢查
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.5.4、MASVS-CODE-4
- **技術要求**：行動應用程式應針對使用者於輸入階段之字串，進行安全檢查
- **檢測基準**：
  - (1) 是否針對預期使用者輸入之字串驗證**型別**（如欄位本身須接受特殊字元，亦屬可預期輸入字串型別）。
  - (2) 是否針對使用者輸入字串驗證**長度**。
- **檢測結果**：
  - `符合要求`：符合所有檢測基準，或未提供字串輸入介面。
  - `不符合要求`：不符合任一檢測基準。
- **審核線索**：檢查各文字輸入欄位（`EditText`、`UITextField`、`TextField`、`Deep Link` / `Intent` 參數）是否具有明確長度上限（`maxLength` / `InputFilter.LengthFilter` / 邏輯驗證）與型別／字元白名單格式檢查。

#### `4.1.5.4.2` 行動應用程式注入攻擊防護機制
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.1.5.4、MASVS-CODE-4
- **技術要求**：行動應用程式應提供相關注入攻擊防護機制
- **檢測基準**：檢查是否防護使用者輸入下列 7 類注入字串之設計（未來若有新型 Injection 亦納入）：
  1. **SQL Injection**（如本地 SQLite 須用參數化查詢 `?`，禁止字串拼接 SQL）
  2. **JavaScript Injection**（WebView 載入 URL/字串須驗證白名單及編碼，防範 XSS）
  3. **Command Injection**（避免將使用者輸入傳入 `Runtime.exec` / shell 指令）
  4. **Local File Inclusion**（檔案路徑操作／`FileProvider`／`openFile` 須防範 `../` 路徑遍歷並正規化校驗）
  5. **XML Injection**（XML 解析禁用外部實體 XXE，建構 XML 須妥善跳脫或使用 DOM/Serializer）
  6. **Format String Injection**（C/C++ NDK 或格式函式不可將使用者輸入直接作為 format string）
  7. **IPC (Inter-process communication) Injection**（驗證來自 `Intent`/`URL Scheme`/`Deep Link` 的外部參數，不可直接轉入 WebView `loadUrl`、SQL 或系統動作）
- **檢測結果**：
  - `符合要求`：符合所有檢測基準，或未提供字串輸入介面。
  - `不符合要求`：不符合任一檢測基準。
- **備註**：雖然有效防護亦應於伺服器端處理，基於防禦縱深原則，**App 本身至少須有初步防護設計**。

### 4.1.5.5. 防止動態分析及竄改（`F` 類進階加測項目）

#### `4.1.5.5.1` 偵測作業系統保護層破解（Root / Jailbreak）

## 4.2. 伺服器端基本資安檢測基準

> 註：4.2.1（伺服器端安全管理：威脅模型分析、機房／雲端服務商優先採用 ISO/IEC 27001 / CSA STAR / ECSA）與 4.2.2 前段（滲透測試：OWASP Testing Guide / OSSTMM / SANS）屬管理與建議指引；唯一強制檢測基準為 **`4.2.2.1.2` Webview 安全檢測**。

#### `4.2.2.1.2` 行動應用程式之 Webview 安全檢測
- **檢測分類**：`L1`、`L2`、`L3`
- **檢測依據**：規範 4.2.2.1、MASVS-NETWORK-2、MASVS-PLATFORM-2
- **技術要求**：行動應用程式於 Webview 呈現功能時，所連線之網域應執行安全檢測
- **檢測基準**：
  - 檢查使用 Webview 呈現功能時，其網頁伺服器弱點掃描須驗證 **Injection Flaws（含 Cross-Site Scripting, XSS）** 檢查是否全數通過。

- **檢測結果**：
  - `符合要求`：符合檢測基準，或於 Webview 呈現功能時無連網（僅載入本地靜態內容）。
  - `不符合要求`：不符合檢測基準。
  - `不適用`：行動應用程式無使用 Webview 呈現功能。
- **補充說明（第 6 節）**：所有第一層之連結均須附弱點掃描報告；弱點掃描須使用行動應用資安聯盟清單內之工具；若伺服器端網頁資訊改版須重新掃描。
- **審核線索**：盤點專案中是否使用 `WebView` / `WKWebView` / `SFSafariViewController` / `webview_flutter` / `react-native-webview`；列出所有 Webview 載入的遠端 URL／網域，並檢查是否於 App 側有網域白名單限制與安全組態；針對遠端網頁弱點掃描結果（Injection Flaws / XSS）於靜態碼層通常須標記為「待人工／動態確認」（並提示補附弱點掃描報告與調查表第 19 項）。
